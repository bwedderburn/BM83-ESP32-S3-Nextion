# Firmware Deployment Guide

> **Installed-controller exception:** the evaluated `10.3.1-dirty` controller
> hard-faults during VM teardown. Its [recovery safeguards](#optional-universe-badge-receiver)
> take precedence over the general copy/soft-reload instructions below.

This guide explains how to deploy updated firmware to your ESP32-S3 device in two explicit modes:

1. **Baseline mode (.py)**: copy plain source files from `firmware/circuitpython/`.
2. **Optimized mode (.mpy)**: build and deploy `dist/circuitpython/` generated by `build_mpy.sh`.

Start with **baseline `.py` mode first** for debugging and reproducibility. After behavior is validated on-device, switch to **optimized `.mpy` mode** for production.

## Pre-Deploy Checklist (Required Order)

Run these checks in order before any production update:

1. **Run host regression tests first** (logic-level protection):
   ```bash
   pytest -q
   ```
   Optional `.mpy` build-path verification:
   ```bash
   RUN_MPY_TESTS=1 pytest -q tests/test_mpy_build.py
   ```
2. **Deploy and validate the device using baseline `.py` files** (Mode A) so behavior is observable and debuggable on hardware.
3. **Roll out optimized `.mpy` artifacts only after baseline validation succeeds** (Mode B).

> Host tests do **not** fully validate hardware behavior (UART timing, RF behavior, target-runtime constraints). See [docs/hardware-test-limitations.md](../validation/hardware-test-limitations.md) for scope and limitations.

### Codex CLI Workflow (Recommended for Bug-Free Rollouts)

If you are using Codex CLI to implement and verify changes, use this repeatable sequence before deploying:

1. Sync and inspect working tree:
   ```bash
   git pull --rebase
   git status --short
   ```
2. Run fast host regression suite:
   ```bash
   pytest -q
   ```
3. Run optional `.mpy` build-path check when touching build/deploy logic:
   ```bash
   RUN_MPY_TESTS=1 pytest -q tests/test_mpy_build.py
   ```
4. Verify no unresolved changes before deploy packaging:
   ```bash
   git diff --stat
   git status
   ```
5. Deploy baseline `.py` first (`./deploy.sh`), then run post-deploy smoke checklist.
6. Only after baseline stability is confirmed, build/deploy `.mpy` **from a clean
   CIRCUITPY filesystem** or after deleting the project module folders under
   `CIRCUITPY/lib/` (`bm83/`, `nextion/`, `blehid/`, and `utils/`) (`./build_mpy.sh`
   + copy `dist/circuitpython/*`), then re-run the same smoke checklist.

This sequence minimizes crash risk by proving deterministic host behavior first, then validating hardware behavior incrementally.

## When to Update Firmware

You need to update the firmware on your ESP32-S3 when:
- You've pulled latest changes from GitHub
- You're seeing garbage bytes in serial output (e.g., `b'BT_POWERf\x00'` instead of `b'BT_POWER'`)
- You want to use new features or bug fixes

## Mode A: Baseline Deployment (.py, recommended first)

### Step 1: Connect to Your Device

Connect your ESP32-S3 to your computer via USB. It should appear as a drive named `CIRCUITPY`.

### Step 2: Deploy Plain Python Sources

Run the deployment script from your repository directory (or copy manually):

```bash
# From your repository directory
./deploy.sh
```

Manual equivalent:

```bash
cp -r firmware/circuitpython/* /path/to/CIRCUITPY/
```

**Important files to update** (if you've made changes):
- `lib/nextion/display.py` - Nextion protocol and token parsing
- `main.py` - Main application logic
- `lib/bm83/bm83.py` - BM83 module updates
- `lib/blehid/ble.py` - BLE HID updates

### Step 3: Verify the Update

1. Open a serial terminal to view output:
   ```bash
   # Linux/Mac
   screen /dev/ttyACM0 115200

   # Or use your preferred serial terminal
   ```

2. Press **Ctrl+D** in the serial terminal (or press the RESET button on the ESP32-S3) to reload the code.

3. Check serial output. If tokens are being cleaned properly, you should see:
   ```
   [NX] Token: b'BT_POWER'      ← Clean token (good!)
   [NX] Token: b'BT_PLAY'       ← Clean token (good!)
   ```

   NOT:
   ```
   [NX] Token: b'BT_POWERf\x00'  ← Garbage bytes (old firmware!)
   ```

## Mode B: Optimized Deployment (.mpy, production)

Use this mode only after baseline `.py` behavior is validated.

### Step 1: Build Optimized Artifacts

Use the CircuitPython **10.3.1** compiler selected by the repository pin. The
automatic download is for **Linux x86_64 / x86_64 WSL only**:

```bash
./scripts/fetch_mpy_cross.sh
bm83_mpy_cross="$PWD/tools/mpy-cross/mpy-cross"
"$bm83_mpy_cross" --version
MPY_CROSS="$bm83_mpy_cross" bash ./build_mpy.sh
```

For **macOS, Linux ARM or Windows Git Bash**, install or build a native
CircuitPython 10.3.1 compiler for the host, then set its path explicitly. The
Linux download does not run directly on macOS or Windows. See
[compiler setup](building.md#prerequisites) for the source and platform choices.

```bash
# Example native macOS path; replace with your actual installed compiler.
bm83_mpy_cross="$HOME/Tools/CircuitPython 10.3.1/mpy-cross"
# Git Bash example instead: bm83_mpy_cross="/c/Tools/CircuitPython 10.3.1/mpy-cross.exe"
"$bm83_mpy_cross" --version
MPY_CROSS="$bm83_mpy_cross" bash ./build_mpy.sh
```

The version output must start with `CircuitPython 10.3.1`; MicroPython's
`mpy-cross` (including the package installed by `pip install mpy-cross`) is a
different compiler. The quoted `MPY_CROSS` path selects the native executable
and supports paths containing spaces.

This creates deployable output under `dist/circuitpython/`.

### Step 2: Deploy Compiled Output

Copy the generated files to `CIRCUITPY`:

```bash
cp -r dist/circuitpython/* /path/to/CIRCUITPY/
```

Ensure required libraries are still present in `CIRCUITPY/lib/`:
- `adafruit_ble/`
- `adafruit_hid/`

### Step 3: Validate Runtime

1. Reset the board.
2. Confirm normal startup and button behavior.
3. Check serial output for regressions.

### Critical Compatibility Warning (`mpy-cross` vs firmware)

The `mpy-cross` version used to compile `.mpy` files must match the CircuitPython firmware version running on the device. The build pins it in `tools/mpy_cross_pin.env` (version + sha256); `build_mpy.sh` rejects any other version, and `dist/BUILD_INFO.txt` records which compiler produced a build.

If versions do not match, you'll typically see:
- `ValueError: incompatible .mpy file`

If that happens:
1. Check the device's `boot_out.txt` against `MPY_CROSS_VERSION` in `tools/mpy_cross_pin.env`. If the device was upgraded, bump the pin (key + sha256) deliberately.
2. Select the correct host compiler using Step 1: Linux x86_64 / x86_64 WSL can use `./scripts/fetch_mpy_cross.sh`; macOS and other hosts need a native CircuitPython compiler selected by `MPY_CROSS`. Check `"$bm83_mpy_cross" --version`, then rebuild with `MPY_CROSS="$bm83_mpy_cross" bash ./build_mpy.sh`.
3. Redeploy `dist/circuitpython/`.

## Quick Rollback: Optimized (.mpy) → Baseline (.py)

If optimized deployment fails, quickly return to known-good source mode:

1. Remove optimized project artifacts from `CIRCUITPY` so CircuitPython cannot import stale `.mpy` modules:
   ```bash
   rm -rf /path/to/CIRCUITPY/lib/bm83
   rm -rf /path/to/CIRCUITPY/lib/nextion
   rm -rf /path/to/CIRCUITPY/lib/blehid
   rm -rf /path/to/CIRCUITPY/lib/utils
   rm -f /path/to/CIRCUITPY/main.py
   ```
2. Re-copy the baseline source tree from `firmware/circuitpython/`:
   ```bash
   cp -r firmware/circuitpython/* /path/to/CIRCUITPY/
   ```
3. Reset the board (`Ctrl+D` or hardware RESET).
4. Re-run baseline validation (token cleanup, BLE connect/pair, metadata refresh, and E-BIND behavior) before proceeding.

## Post-Deploy Smoke Checklist (Project-Specific)

Run this after **every** deployment (baseline or optimized):

- [ ] **UART token cleanliness:** in serial logs, confirm Nextion tokens are clean (e.g., `b'BT_POWER'`) with no garbage suffix bytes.
- [ ] **BLE connect/pair flow:** confirm device advertises, connects, and reaches encrypted/paired state (`[BLE] Connected`, `[BLE] Paired/encrypted`).
- [ ] **Metadata refresh path:** trigger track/source changes and verify metadata text is refreshed on the Nextion display.
- [ ] **E-BIND behavior:** confirm expected E-BIND startup/initialization behavior is present and does not regress normal control flow.
- [ ] **No startup regressions:** board boots without traceback and button actions still map correctly.

## Full Deployment (Clean Install)

If you want to do a complete fresh install:

### Step 1: Flash CircuitPython

If you haven't already, flash CircuitPython 10.x to your ESP32-S3 DevKitC-1:
1. Download the appropriate CircuitPython .uf2 file for ESP32-S3
2. Put the board into bootloader mode
3. Copy the .uf2 file to the USB drive that appears

### Step 2: Install Required Libraries

Copy the required CircuitPython libraries to the `lib` folder on your `CIRCUITPY` drive:
- `adafruit_ble`
- `adafruit_hid`

These can be downloaded from the [CircuitPython Library Bundle](https://circuitpython.org/libraries).

### Step 3: Choose Deployment Mode

- Baseline mode: copy `firmware/circuitpython/*`
- Optimized mode: run `./build_mpy.sh` then copy `dist/circuitpython/*`

### Step 4: Verify Installation

1. The board should auto-reset and start running.
2. Connect via serial terminal to view output.
3. Check that tokens are being parsed correctly (no garbage bytes).

## Troubleshooting

### Still Seeing Garbage Bytes After Update

If you're still seeing tokens like `b'BT_POWERf\x00'` after updating:

1. **Verify the files were copied correctly:**
   ```bash
   # Check the modification time of display.py on the device
   ls -l /path/to/CIRCUITPY/lib/nextion/display.py
   ```
   
2. **Ensure code reloaded:**
   - Press **Ctrl+D** in the serial terminal
   - Or press the **RESET** button on the board
   - Or disconnect/reconnect USB

3. **Check you copied the right version:**
   ```bash
   # On your computer, verify you have the latest code
   cd /path/to/BM83-ESP32-S3-Nextion
   git pull
   git log --oneline -3
   ```
   
   You should see recent commits with message "Fix token parsing to extract clean tokens without garbage bytes"

4. **Restore the deployed modules:**
   In optimized mode, `lib/nextion/*.mpy` files are live modules, not a cache. Rebuild
   and redeploy the optimized artifacts:
   ```bash
   ./build_mpy.sh
   cp -r dist/circuitpython/* /path/to/CIRCUITPY/
   ```
   Or switch to baseline mode by copying `firmware/circuitpython/*` over the existing
   files on `CIRCUITPY`.

### Buttons Still Don't Work

If tokens are clean (`b'BT_POWER'`) but buttons don't trigger actions:

1. **Check BLE pairing** (for volume buttons):
   - Ensure ESP32-S3 is paired with your device
   - Look for `[BLE] Connected` and `[BLE] Paired/encrypted` in serial output
   - Volume buttons require BLE HID connection

2. **Check token allowlist:**
   - Verify your tokens are in `TOKENS` set in `nextion/display.py`
   - For volume: `BT_VOLUP_P`, `BT_VOLUP_R`, `BT_VOLDN_P`, `BT_VOLDN_R`

3. **Check Nextion configuration:**
   - Verify Touch Press and Touch Release events are configured
   - Use `print "TOKEN"` commands (not `printh`)

### Board Won't Start After Update

If the board shows errors or won't start:

1. **Check serial output for errors:**
   Connect via serial terminal and look for Python tracebacks

2. **Verify file integrity:**
   Ensure all files copied completely (no truncated files)

3. **Test with known-good code:**
   Copy files from a known-working commit

4. **Factory reset:**
   - Reflash CircuitPython
   - Redeploy from scratch following "Full Deployment" steps

## Optional Universe badge receiver

The BMW1 receiver is `lib/remote/badge_remote.py` (or its compiled `.mpy`).
It is inert without the private `/.badge_remote.json` profile. The profile
requires `v: 1`, a 64-character lowercase hexadecimal `key`, and optionally
`port` (default 8767), `client_ip`, and `allow_bond_erase` (default false).
The badge's root `secrets.py` uses the matching `BM83_HOST`, `BM83_PORT` and
`BM83_KEY`. Never commit filled profiles, keys, network details, or device
captures. Activating a listener or provisioning credentials requires explicit
owner approval.

The receiver uses an already connected Wi-Fi radio; it does not configure or
join a network itself. Authenticated BMW1 requests receive cached Now Playing
and BLE status. `src=mac` identifies the Mac Wi-Fi metadata bridge and
`src=avrcp` identifies native metadata; an empty source is not proof of either.
UART acknowledgments and working audio alone do not prove metadata delivery.

**Runtime limitation:** the installed CircuitPython 10.3.1-dirty runtime has been
observed hard-faulting during VM teardown, including after Ctrl-C with playback
paused and before any filesystem write. Do not treat a running-filesystem
copy or a soft reload as a safe deployment. The controller's `boot.py` disables
automatic reload on CIRCUITPY writes while keeping the USB drive available.
Pause the source and confirm the controller is stopped at the REPL with
autoreload disabled or in safe mode. Install and hash-verify only the approved
delta, preserve the other startup files, profiles, and bonds, and request a
deliberate normal restart. If stopping enters safe mode, retain
the fault evidence; after verification, an ESP32-only
`microcontroller.reset()` from the safe-mode REPL has restored normal startup.
This is a recovery procedure, not a fix for the runtime fault. Do not
reflash, erase bonds, or change configuration as a workaround.

BMW1 `NET_RETRY` is always refused with `denied=true`, including duplicate
requests; no reload token is dispatched. This protects older badge clients
too. The badge settings retry is badge-local Wi-Fi/artwork recovery only.
The shared non-BMW1 artwork retry now requests `microcontroller.reset()`, not
`supervisor.reload()`. It retains existing-profile validation and never joins
Wi-Fi in the hot UART loop. It refuses the request whenever USB is enumerated,
even if its serial console is closed, and when the USB-state API is unavailable
or unreadable. Safely eject and disconnect USB before a separately authorized
remote retry; ejection alone is not inferred from serial state. The guard also
covers injected reset callbacks. If the hard-reset API is unavailable it logs an
explicit refusal, with no soft-reload fallback. The injectable `reload_fn`
argument is retained for existing host callers. This candidate mitigation still
requires a live retry regression; a successful safe-mode recovery is not that
test. Bond erasure remains refused unless separately opted in; allowing bond
erasure does not enable BMW1 receiver retry.

The receiver now reuses an active HELLO nonce without resetting command sequence
watermarks. A fixed 512-byte per-activation ledger prevents retired HELLO packets
from repeatedly evicting current clients. It admits at most 64 unique nonces per
activation; after that it fails closed for new handshakes while established
clients, active retries and required volume releases continue. A separately
requested local restart is needed before further new sessions. This bounded
resource tradeoff changes no wire format or key and has only host validation.
BLE observations are withheld while same-pass BLE commands await dispatch, and
the 20 ms packet limiter uses wrap-safe integer ticks rather than float uptime.
None of these changes establishes radio stability or physical acceptance.

The one-time `tools/provision_artwork_wifi.py` utility still uses Ctrl-D after
stopping the controller. Do not run it unmodified on this faulting runtime.
Recover the controller first and check existing links before reprovisioning.
Any necessary USB setup must use a fresh on-panel Save, private profile
comparison/backup, and a separately verified stopped-runtime/hard-reset path.

Pre-recovery validation (2026-11-01): 1,239 host tests passed with one skip, strict
CI lint passed, and the badge add-on/mirror passed parity checks. The subsequent
shared-retry candidate passed 79 focused receiver/retry/main-loop tests. The official
simulator covered 29 cases; a receive-error message frame remains unverified
there. Authenticated receiver STATUS and retry refusal were checked on the
controller. The badge app was installed and hash-verified, and its owner
confirmed RESET and launch. During the subsequent physical run, a passive
capture showed the shared Wi-Fi retry log followed by VM teardown and safe
mode, without an accepted BMW1 `NET_RETRY` in that capture. The originating
input is not established. The shared retry candidate was subsequently installed
as the only file delta from confirmed safe mode, followed by an ESP32-only hard
reset. Boot, Wi-Fi and receiver readiness returned; authenticated title/artist
matched Music with `src=mac`. CrowPanel passive telemetry showed fresh playback
snapshots with an advancing clock. Playback state/position were restored and
volumes were unchanged. Existing files, keys and profiles were preserved.
